# Budcom Tally Connector – Permanent Engineering Rules

Version: 1.0
Status: PERMANENT
Priority: HIGHEST

---

# Philosophy

The Budcom Tally Connector is an enterprise-grade communication layer between Budcom and TallyPrime.

Its primary responsibility is:

- Never corrupt customer data.
- Never crash Tally.
- Never perform unintended writes.
- Never trust unknown XML.
- Never sacrifice safety for convenience.
- Always fail safely.

Performance is secondary.
Features are secondary.
Architecture and reliability are permanent.

---

# Core Principle

The connector exists to safely communicate with Tally.

It is NOT business logic.

It is NOT an inventory system.

It is NOT an accounting engine.

It is a secure communication layer.

---

# Read-Only by Design

Production communication with Tally shall always be read-only.

Forbidden operations include:

- IMPORT
- EXECUTE
- FUNCTION
- CREATE
- ALTER
- DELETE
- UPDATE
- Any write-capable XML request

Unknown operations are forbidden.

Unknown means DENY.

---

# No Raw XML

Application code must never generate XML directly.

Application code must never send XML directly.

All XML must be generated by the approved XML builder.

There shall never be a public:

sendXml()

executeXml()

rawTransport()

executeRaw()

or equivalent API.

---

# Single Communication Gateway

Every request must flow through ONE pipeline.

Business Request
↓

Validation
↓

Policy Engine
↓

Capability Check
↓

Registry Lookup
↓

Health Check
↓

XML Builder
↓

Transport
↓

Parser
↓

Normalization
↓

Audit

No component may bypass this pipeline.

---

# Fail Closed

When uncertain:

Reject.

Never guess.

Never continue.

Never retry dangerous requests.

UNKNOWN = DENY

---

# Capability Model

Every request must declare an explicit capability.

Example:

- TALLY_HEALTH_READ
- TALLY_COMPANY_READ
- TALLY_MASTER_READ
- TALLY_REPORT_READ

No generic capability shall exist.

---

# Registry Driven

Requests are approved by registry.

Registry stores:

- operation id
- ERP
- capability
- XML template
- timeout
- parser
- risk
- version
- evidence
- regression tests

Hard-coded request logic is prohibited.

---

# Safety Registry

Operations are classified:

VERIFIED_SAFE

CONDITIONAL

EXPERIMENTAL_DISABLED

FORBIDDEN

UNKNOWN

Only VERIFIED_SAFE may execute automatically.

---

# Health Policy

Every business request requires:

Pre-flight health check.

Business request.

Post-flight health check.

After timeout:

Open circuit.

Enter quarantine.

Require successful health verification.

No business request may exit quarantine.

---

# Circuit Breaker

States:

AVAILABLE

SUSPECTED

QUARANTINED

RECOVERING

Only health requests may run while recovering.

---

# No Automatic Retries

Business requests are never blindly retried.

Retries may create instability.

Only explicitly safe health probes may retry.

---

# Offline XML Import

Offline XML Import is NOT Tally IMPORT.

Offline import means:

User XML

↓

Validation

↓

Parser

↓

Normalization

↓

Local Budcom Database

↓

Complete

Offline XML must never be transmitted back to Tally.

---

# Dependency Rules

Business logic may not access:

- HTTP
- Fetch
- Socket
- XML Builder
- Transport

Only the connector gateway may communicate with Tally.

---

# ERP Independence

The safety engine must remain ERP independent.

Only adapters change.

Example future adapters:

Tally

BUSY

Marg

SAP

Zoho

ERPNext

Business logic must never know which ERP is connected.

---

# Logging

Every request logs:

Correlation ID

Operation

Capability

Registry Version

Duration

Result

Circuit State

Health Before

Health After

No sensitive XML shall appear in production logs.

---

# Dangerous XML

Known dangerous XML shall remain permanently blocked.

Regression tests shall ensure they never execute again.

Previously failing payloads are permanent test cases.

---

# Testing Requirements

Every new endpoint requires:

Unit tests

Integration tests

Regression tests

Failure tests

Timeout tests

Malformed XML tests

Health recovery tests

Architecture boundary tests

A feature without tests is incomplete.

---

# Architecture Rules

Never expose transport publicly.

Never expose XML builder publicly.

Never expose raw HTTP publicly.

No future developer shall bypass the gateway accidentally.

Architecture must enforce safety.

Not documentation.

Not comments.

---

# SOLID

Every module shall:

Have one responsibility.

Depend upon abstractions.

Remain independently testable.

Avoid circular dependencies.

---

# Backward Compatibility

Never silently change XML contracts.

Version parsers.

Version normalizers.

Detect schema drift.

Return INCOMPLETE instead of incorrect data.

---

# Production Principles

Fail safely.

Fail visibly.

Never fail silently.

Never damage Tally.

Never damage customer data.

Never hide uncertainty.

---

✓ Lint passes

✓ Tests pass

The connector shall always be designed so that:

"No future feature, developer, AI assistant, or accidental code change can make Budcom crash Tally or perform unintended writes."
